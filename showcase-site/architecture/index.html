01

시스템 범위와 문서 전제

지금 저장소는 공개 랜딩, 내부 실무 대시보드, 운영 패널, 그리고 이를 받치는 자동화 백엔드가 한 저장소 안에 함께 구성된 형태입니다. 하나의 FastAPI 코어가 이 전체를 연결하고 있고, 그 중심에는 카드사별로 다른 흐름을 하나의 자동화 체계로 묶어낸 백엔드가 있습니다.

app.py database.py modules/connectors/*

공개 랜딩

entry-page/index.html 기반 정적 페이지. FastAPI가 파일과 자산을 서빙합니다.

내부 실무 대시보드

templates/simple_dashboard.html 와 static/js/dashboard.js 가 중심입니다.

운영 패널

templates/ops_dashboard.html 와 static/js/ops.js 로 동기화와 작업 상태를 제어합니다.

자동화 백엔드

app.py, modules/, database.py 가 카드사 수집 · 추출 · 정규화 · 인사이트 · 리포트까지 묶는 코어 역할을 합니다.

핵심 관점

현재 구조를 이해할 때는 "기능이 무엇이 있나"보다 "서로 다른 카드사 업무를 어디까지 자동화했고, 그 자동화가 어떤 화면과 저장소와 API에 걸쳐 있는가"를 파악하는 것이 핵심입니다.

현재 구조에 이미 반영된 자동화 범위

복잡성의 상당 부분은 카드사별로 다르게 처리해야 하는 작업을 하나의 운영 흐름으로 자동화한 결과입니다.

자동화 파이프라인 흐름
flowchart LR C1["삼성카드"] --> X["connector registry"] C2["신한카드"] --> X C3["현대카드"] --> X C4["KB국민카드"] --> X X --> I["ingest"] I --> E["extract detail"] E --> N["normalize"] N --> H["insight"] H --> J["jobs and status tracking"] J --> D["dashboard and ops"] J --> R["briefing and report"] N --> P["products and disclosures"] P --> G["rag and catalog"]

4개 카드사의 수집 결과가 하나의 정규화 파이프라인으로 합류하는 전체 흐름

공통 자동화 계약

BaseConnector모든 카드사 커넥터는 공통 베이스 클래스를 상속하고, 최종적으로 동일한 RawEvent 스키마를 반환합니다.
CONNECTORS registry삼성카드, 신한카드, 현대카드, KB국민카드를 하나의 registry로 묶고 파이프라인이 회사명 기준으로 순회합니다.
URL 정규화공통 유틸에서 상대경로 보정, 추적용 query 제거, 정렬, canonical URL 생성까지 수행해 카드사별 링크 형식을 한 기준으로 맞춥니다.
기간/카테고리/위협도각 카드사 원본 텍스트에서 기간 문자열을 공통 포맷으로 정리하고, 키워드 기반 카테고리와 혜택 강도 기반 threat level 추론을 공통 계층에서 처리합니다.
후속 파이프라인수집 결과는 다시 extract detail → normalize → generate_hybrid_insight → jobs/status tracking 흐름으로 이어져 개별 카드사 차이를 내부 공통 모델로 흡수합니다.

파이프라인에서 자동화되는 운영 포인트

회사 단위 ingestrun_ingest() 가 registry를 순회하면서 카드사별 수집을 실행하고, 회사별 job row와 timeout, 성공/실패 수를 함께 기록합니다.
미추출 이벤트 후속 처리run_extract_and_enrich() 가 수집 이후의 상세 추출, 정규화, 인사이트 생성을 이벤트 단위로 이어받아 저장합니다.
운영 패널 연결자동화 진행 상태는 /api/pipeline/progress, /api/jobs, sync-status 계열 API를 통해 내부 대시보드와 운영 패널에서 바로 소비됩니다.
후속 자산 연결정규화 결과는 상품/공시 연결, RAG 문서 탐색, 브리핑/리포트 근거 데이터까지 이어져 카드사별 차이가 화면 단에서는 공통된 제품 경험으로 보이게 됩니다.

삼성카드 커넥터

  • 목록 페이지 DOM을 직접 긁는 대신, 실제 프런트가 호출하는 frontservice/SHPPBE1401S02 JSON 계약을 재사용합니다.
  • totCt, pageRowsSize 값을 읽어 총 페이지 수를 계산하고, 페이지 번호를 올리며 안정적으로 순회합니다.
  • cmsId, cmpId, cmpCriDvC, massCmpDvC 를 조합해 일반 이벤트, mass campaign, premium S Lounge 상세 URL을 분기 생성합니다.
  • 즉 삼성은 "렌더된 카드 목록"이 아니라 "실서비스 목록 API 계약"을 직접 흡수해 자동화한 케이스입니다.

신한카드 커넥터

  • 단일 소스에 의존하지 않고 evnPgsList01~03.json 정적 JSON, MOBFM829R03.ajax 모바일 AJAX, DOM 파싱을 우선순위 fallback 체인으로 묶습니다.
  • JSON 응답에서는 mobWbEvtNm, evtImgSlTilNm, evtImgRplNm 같은 복수 필드 후보를 흡수해 제목을 표준화합니다.
  • DOM fallback에서는 실제 모바일 이벤트 목록을 열고 여러 차례 scroll 하며 lazy-loaded 항목을 확보한 뒤, 링크/블록 텍스트에서 기간과 제목을 재구성합니다.
  • 즉 신한은 "소스가 하나가 아닌 사이트"를 다층 fallback 자동화로 커버한 케이스입니다.

현대카드 커넥터

  • 우선 DOM 기반으로 #event_list1 li 를 읽고, #moreDiv .btn-more 버튼을 반복 클릭해 목록을 끝까지 확장합니다.
  • 버튼이 더 이상 이벤트 수를 늘리지 않으면 stagnation 조건으로 루프를 종료해, "더보기 기반 목록"을 안정적으로 수집합니다.
  • DOM 수집량이 충분하지 않을 때는 /cpb/ev/apiCPBEV0101_05s.hc 를 직접 호출해 rnum, index, searchWord, evntCtgrVl 기반 페이지네이션을 이어갑니다.
  • bnftWebEvntCd 로 상세 URL을 재조립하고, DOM/내부 API를 함께 활용해 자동화 안정성을 높인 케이스입니다.

KB국민카드 커넥터

  • 목록 페이지가 javascript:goDetail() 와 doSearchSpider(pageCount) 패턴을 쓰기 때문에, 브라우저 클릭 대신 form POST 기반으로 페이지를 직접 순회합니다.
  • pageCount 를 1부터 증가시키며 HTML을 받아오고, 앵커의 javascript 인자에서 eventNum 을 추출해 상세 URL을 재구성합니다.
  • 제목은 우선 셀렉터 기반으로 읽고, 실패하면 이미지 alt, 마지막으로 텍스트 블록 정제로 fallback 하며, 기간은 연도 생략 종료일도 보정합니다.
  • 즉 KB는 "javascript 링크와 서버 렌더 HTML" 중심 구조를 안정적으로 자동화한 케이스입니다.

카드사별 차이를 흡수하는 방식

삼성카드실서비스 목록 API 계약을 직접 사용해 안정적으로 목록을 가져오고, 세부 파라미터를 조합해 이벤트 상세 URL까지 재구성합니다.
신한카드정적 JSON, 모바일 AJAX, DOM fallback을 계층적으로 묶어 한 소스 변경이 전체 수집 실패로 번지지 않게 합니다.
현대카드DOM 더보기 반복과 내부 API 직접 호출을 함께 사용해 사용자 화면 기준 목록과 비가시 목록을 모두 자동화합니다.
KB국민카드javascript 링크와 form POST 페이지네이션을 해석해 서버 렌더 HTML 구조를 표준 수집 흐름으로 변환합니다.

자동화 결과가 이어지는 공통 출력

RawEvent모든 카드사 원본 수집 결과는 URL, 회사명, 제목, 기간, 카테고리, 혜택 정보, raw_text를 가진 공통 구조로 정렬됩니다.
이벤트 저장공통 구조는 이후 CardEvent 와 관련 스냅샷/섹션/인사이트 모델로 저장돼 화면과 분석 API의 공통 입력이 됩니다.
브리핑과 리포트수집 및 정규화 결과는 회사별 briefing payload, report snapshot, PDF artifact 생성의 근거 데이터로 재사용됩니다.
상품 · 공시 · RAG같은 결과가 상품 카탈로그, 공시 payload, launch authority, document search, RAG catalog로 다시 연결됩니다.
커넥터 구조 요약

modules/connectors/base.py 의 공통 계약이 먼저 있고, 각 카드사 커넥터는 그 위에 "목록을 어디서 읽는가", "상세 URL을 어떻게 복원하는가", "기간과 제목을 어느 단계에서 보정하는가"를 다르게 구현합니다. 현재 As-Is의 중요한 성과는 이 차이를 커넥터 내부로 흡수해, 파이프라인과 화면 계층에서는 네 카드사를 거의 같은 타입처럼 다룰 수 있게 만든 점입니다.

02

앱 기동과 초기화 구조

app.py 는 단순 라우터 파일이 아닙니다. 앱 생성, 정적 경로 마운트, 템플릿 준비, 브리핑 라우터 포함, 이후 대부분의 페이지/API 선언이 모두 여기서 일어납니다. 현재 자동화 흐름을 한 코어 안에서 운영하기 때문에 이 파일의 역할도 자연스럽게 넓어져 있습니다.

app.py routers/briefing.py modules/dashboard_snapshot.py

기동 순서

현재 구조는 앱 구성과 주요 응답 흐름을 한곳에서 조립하는 중심 파일에 가깝습니다.

FastAPI 부팅 시퀀스
flowchart TB A["process start"] --> B["import app.py"] B --> C["FastAPI()"] C --> D["mount /static"] D --> E["mount /entry-page"] E --> F["mount /image"] F --> G["mount /card-terms"] G --> H["Jinja2Templates('templates')"] H --> I["include briefing_router"] I --> J["register page routes"] J --> K["register API routes"] K --> L["serve requests"]

단일 프로세스에서 정적 자산, 템플릿, 라우터, API가 순차적으로 조립되는 과정

정적 마운트와 템플릿 준비

/static대시보드/운영 패널 공용 JS, CSS, favicon
/entry-page공개 랜딩의 CSS/JS/정적 자산
/image이미지 자산
/card-terms약관 PDF와 원본 문서 접근 경로

초기화 시점에 조립되는 책임

app.py페이지/API/캐시/락/동기화 시작/응답 조립
routers/briefing.py부분 분리된 유일한 독립 라우터
modules/*브리핑, 파이프라인, 상품, 신호, RAG, 리포트 서비스

기동 시점 전역 상태

  • _COMPANY_BRIEF_CACHE, _QUAL_COMPARISON_CACHE, _WEEKLY_AI_INSIGHT_CACHE 같은 메모리 캐시를 앱 레벨에서 유지합니다.
  • _DISCLOSURE_SYNC_LOCK, _LAUNCH_AUTHORITY_SYNC_LOCK, _PRODUCT_SYNC_LOCK, _NAVER_SIGNAL_SYNC_LOCK 로 동기화 중복 실행을 제어합니다.
  • 서울 시간대 기준 유틸과 간단 캐시 TTL이 부팅 시 같이 준비됩니다.

기동 시점 주요 모듈 의존성

  • modules.dashboard_snapshot 는 탭별 snapshot payload를 생성하고 메타를 유지합니다.
  • modules.launch_authority_source, modules.naver_signals, modules.kosis_stats, modules.naver_news 는 외부 데이터 소스를 붙입니다.
  • modules.product_links 는 상품 카탈로그, 문서 검색, PDF 링크, catalog stats를 제공합니다.
  • routers.briefing 는 브리핑/리포트 관련 라우트를 앱에 포함시킵니다.
왜 이 구조가 중요한가

현재 구조에서 FastAPI 앱 생성은 단순 웹서버 기동이 아니라, 캐시 초기화, 동기화 잠금 준비, 정적 자산 노출, 템플릿 엔진 준비, 브리핑 라우터 연결까지 포함한 운영 surface 조립 과정입니다. 따라서 부팅 구조를 읽는 것은 곧 "이 시스템이 무엇을 한 프로세스 안에서 책임지는가"를 읽는 일입니다.

03

화면 진입 구조

가장 먼저 잡아야 할 사실은 메인 루트가 공개 랜딩이 아니라 내부 대시보드라는 점입니다. 외부 진입과 내부 진입이 서로 다른 목적에 맞춰 나뉘어 있습니다.

app.py templates/simple_dashboard.html templates/ops_dashboard.html entry-page/index.html

현재 페이지 라우트

페이지 수는 적지만 의미가 강하게 다릅니다. 공개, 내부, 운영이 같은 앱 안에 공존합니다.

페이지 라우트 맵
flowchart LR A["FastAPI pages"] --> B["/ -> simple_dashboard.html"] A --> C["/entry -> FileResponse(entry-page/index.html)"] A --> D["/ops -> ops_dashboard.html"] A --> E["/luxury -> redirect /"] A --> F["/pro -> redirect /"] A --> G["/index -> redirect /"]

공개/내부/운영 세 가지 목적이 하나의 FastAPI 앱에서 공존하는 구조

구조적 의미

공개 랜딩은 존재하지만 메인 엔트리가 아닙니다. 그래서 브라우저 루트로 들어오면 외부 소개가 아니라 내부 실무 화면이 열립니다. 이건 배포, 인증, 공유 URL 설계에 모두 영향을 줍니다.

현재 진입면 역할

공개용/entry + entry-page/
실무용/ + simple_dashboard.html
운영용/ops + ops_dashboard.html

/ 내부 대시보드

  • simple_dashboard.html 을 렌더링하고, 기본 실무 진입면 역할을 합니다.
  • 동시에 report mode preview surface로도 재사용됩니다.
  • mode=report, report_type, basis 쿼리로 일간/주간/월간 리포트 화면을 구성합니다.

/entry 공개 랜딩

  • entry-page/index.html 을 FileResponse 로 직접 반환합니다.
  • CSS/JS는 /entry-page static mount 아래에서 별도로 로드됩니다.
  • 즉 Jinja 기반 페이지가 아니라 순수 정적 랜딩 경로입니다.

/ops 운영 패널

  • ops_dashboard.html 을 렌더링하며 파이프라인, 공시, 상품, RAG sync의 제어면 역할을 합니다.
  • 조회보다 실행 상태와 진행률, 재시도에 더 초점이 맞춰져 있습니다.

snapshot 라우트

  • /api/dashboard/snapshot/meta 는 snapshot 메타와 탭별 captured_at 정보를 제공합니다.
  • /api/dashboard/snapshot/{tab} 는 dashboard/events/products/insights 탭별 payload를 반환합니다.
  • /api/dashboard/snapshot/refresh 는 refresh를 트리거해 리포트 스튜디오와 연결됩니다.

루트 페이지의 report mode 재사용

query contractmode=report 일 때 같은 템플릿이 리포트 화면처럼 동작하며, report_type 은 daily/weekly/monthly, basis 는 날짜 또는 월 기준값으로 해석됩니다.
report studio 연결modules.report_studio.build_report_preview_route_url() 는 바로 이 루트 페이지를 리포트 preview surface로 사용하도록 URL을 만듭니다.
snapshot 근거report preview와 artifact manifest는 snapshot meta의 captured_at 값을 근거 시각으로 사용합니다.

페이지 라우트와 API 라우트의 연결점

/대시보드 화면 렌더링 이후, 실제 데이터는 JS가 API를 호출해 조립합니다.
/ops운영 패널 렌더링 이후, sync/status/retry 실행은 모두 POST/GET API를 통해 이어집니다.
snapshot APIs페이지가 직접 호출하지 않아도 리포트와 운영 흐름에서 재사용 가능한 별도 읽기 계층으로 존재합니다.

어떤 화면이 어떤 JS를 쓰고, 그 JS가 어느 API 묶음을 때리는지를 보면 현재 구조가 선명해집니다.

프론트엔드 의존성 그래프

각 화면이 어떤 JS를 통해 어떤 API 영역과 연결되는지 보여주는 의존성 맵

entry-page/

공개 소개용 정적 페이지. HTML/CSS/JS가 완전히 독립입니다.

templates/simple_dashboard.html

내부 대시보드 렌더링. 실제 데이터 시각화와 상세 패널이 여기로 몰립니다.

static/js/dashboard.js

내부 앱의 핵심 프론트 컨트롤러 역할. 여러 API 영역을 직접 연결해 화면을 조립합니다.

static/js/ops.js

운영 패널에서 파이프라인, 동기화, 작업 상태 제어를 담당합니다.

내부 대시보드 템플릿 계약

simple_dashboard.htmlTailwind CDN, Chart.js, XLSX, 모달 구조, 섹션 카드, report mode title 분기를 템플릿 수준에서 준비합니다.
dashboard.js/api/disclosures, /api/rag/catalog, /api/pipeline/progress, /api/rag/stats, launch authority sync-status 등 여러 API를 호출해 화면을 조립합니다.
dashboard_extras.js리포트 모드와 부가 상호작용, 보조 패널 같은 확장 동작을 별도 스크립트로 분리합니다.

브리핑 · 리포트 프런트 연결

리포트 미리보기 URLreport_studio.build_report_preview_route_url() 가 루트 경로에 report query를 붙여 preview URL을 생성합니다.
브리핑 preview/api/briefing/preview 는 HTMLResponse를 직접 반환하고, 요청 기준 dashboard URL을 다시 해석해 링크를 맞춥니다.
snapshot 의존성리포트 manifest는 dashboard snapshot meta와 tab capture 시각을 읽어 preview, artifact, basis timestamp를 연결합니다.

dashboard.js 주요 호출면

  • /api/disclosures?new_only=false 로 최근 상품/공시 목록을 가져옵니다.
  • /api/rag/catalog?limit=5000 로 상품 카탈로그를 불러옵니다.
  • /api/pipeline/progress, /api/rag/stats, /api/disclosures/stats 로 운영 상태를 같이 노출합니다.
  • /api/disclosures/sync-status, /api/products/launch-authority/sync-status 를 호출해 자동화 상태를 사용자 화면에도 보여줍니다.

ops.js 주요 호출면

  • 파이프라인 실행, 작업 재시도, 진행률 폴링, 공시/상품 sync 실행을 담당합니다.
  • 즉 운영 패널 프런트는 "분석용 UI"가 아니라 "실행형 오퍼레이터 콘솔"에 가깝습니다.

entry-page 프런트 특징

  • 백엔드 데이터 fetch 의존 없이 독립적으로 동작하는 마케팅/소개용 정적 프런트입니다.
  • 운영/분석 UI와 자산 체계가 분리돼 있어 외부 공개용 얼굴 역할을 수행합니다.

브리핑/리포트 프런트 특징

  • 브리핑 preview는 API가 HTML을 바로 반환하는 server-rendered 성격입니다.
  • 리포트 preview는 루트 페이지를 iframe 기반 preview shell에 넣는 방식이라, 기존 대시보드 surface를 재활용합니다.

무게 중심은 화면보다 API 계층에 있습니다. 이벤트와 분석만 큰 게 아니라 상품, 공시, RAG, 파이프라인, 운영 연동까지 같은 앱 파일에서 직접 노출됩니다. 이것은 곧 카드사별로 다른 수집과 해석 작업이 API 계층에서 자동화되고 있다는 뜻이기도 합니다.

도메인 구성 특징

부분 분리브리핑만 routers/briefing.py 로 빠져 있고 대부분은 app.py 에 남아 있습니다.
현재 구성조회 API, 운영 제어 API, 백그라운드 동기화 시작 API가 같은 라우트 계층에서 함께 운영됩니다.
공유 경계실무 화면과 운영 패널이 일부 같은 API 도메인을 함께 씁니다.

events 영역

  • 리스트/상세 조회 외에 review queue, extract-detail, batch delete, manual-update, lock, edit-history까지 포함합니다.
  • 즉 단순 조회 API가 아니라 사람 개입과 큐레이션 워크플로우를 품은 도메인입니다.

analytics 영역

  • company overview, workspace bridge, objective scoreboard, strategy map, compare matrix, shinhan gap, qualitative comparison이 포함됩니다.
  • 주간 AI 인사이트, Naver signals, KOSIS approvals까지 외부 데이터 요약 API도 이 영역에 들어 있습니다.

products / disclosures / rag 영역

  • 상품 카탈로그, launch authority, 공시 payload, document search, PDF route, catalog route, RAG build/reindex/search가 하나의 제품군처럼 연결됩니다.
  • 정규화 결과와 문서 저장소가 여기에서 다시 검색/조회 가능한 자산으로 바뀝니다.

briefing / reporting / health

  • routers/briefing.py 는 preview, status, send-now, artifact file response를 제공합니다.
  • /health 는 단순 헬스체크를 제공하고, 실제 운영 상태는 jobs/progress/sync-status 계열 API를 통해 더 풍부하게 관찰됩니다.
API 계층의 설계 원칙

현재 API는 단순 REST 자원 묶음이 아니라, 조회 · 비교 · 운영 제어 · 문서 검색 · 리포트 · 외부 시그널을 함께 제공하는 운영형 surface입니다. 따라서 도메인별 설명을 읽을 때는 "무슨 CRUD가 있나"보다 "이 API가 실무 화면, 운영 패널, 브리핑/리포트 중 어느 흐름에 기여하는가"를 기준으로 보는 편이 정확합니다.

주간 변화 집계 방식

weekly source 범위modules.briefing 는 weekly payload 생성 시 신규 이벤트, 종료 이벤트, active 이벤트, 상품 카탈로그, 외부 시그널을 함께 읽어 source set을 만듭니다.
상품 변화 판정_is_weekly_product_change() 가 launch_date 기준으로 이번 주 범위 안에 들어온 상품을 판정하고, _build_weekly_product_changes() 가 이를 최종 요약 목록으로 추립니다.
회사별 narrative_build_weekly_company_narratives() 는 카테고리 mix, focus products, product changes, external signal 요약을 합성해 회사별 주간 narrative를 만듭니다.
결과 출력weekly briefing payload에는 company stats, category distribution, notable events, product summary, product changes, weekly company narratives가 함께 실립니다.

검색 기준과 매칭 기준

event → product 매칭match_linked_cards() 가 회사 alias, 노이즈 제거, 텍스트 정규화, score threshold를 적용해 자유 텍스트를 canonical product로 고정합니다.
catalog 검색/api/rag/search 는 merged catalog 기준 lexical search를 수행하고, 제품별 메타데이터와 문자열 힌트를 중심으로 찾습니다.
document search/api/products/document-search 는 chunk-level semantic search 후 lexical fallback을 걸어 상품 문서 본문에서 근거를 찾습니다.
뉴스 검색modules.naver_news 는 product/event query variant, dedupe, 발행일 normalization, 제품 출시일 기준 ±3개월 윈도우 판정을 함께 사용합니다.

NAVER DataLab

  • modules.naver_signals 는 NAVER_CLIENT_ID, NAVER_CLIENT_SECRET 기반으로 DataLab search trend를 수집합니다.
  • naver_signal_keywords.json 설정과 tiered card group selection policy를 읽어 카드별/테마별 검색어 세트를 구성합니다.
  • ExternalSignalSnapshot 과 연계돼 월별/기간별 관심도 비교 surface로 재사용됩니다.

NAVER News

  • modules.naver_news 는 news search API를 사용해 event/product 관련 기사 묶음을 만듭니다.
  • query variant, title/url dedupe, press name 추출, launch-date window 판단, score_event_news_match 로 후처리합니다.

KOSIS 통계청 API

  • modules.kosis_stats 는 카드 승인실적 OpenAPI를 호출해 월간 업종별 카드 승인금액을 가져옵니다.
  • 기본 파라미터는 월간 기준, 최근 6개월, 표 DT_435001N_001 기준이며 1시간 캐시를 사용합니다.
  • 업종 한글 축약과 이벤트 카테고리 매핑까지 함께 수행해 인사이트 탭에서 바로 쓰이는 형태로 변환합니다.

외부 연동이 실무에 연결되는 방식

  • NAVER DataLab은 카드/테마 관심도 변화 근거를 제공합니다.
  • NAVER News는 신규 상품/이벤트 관련 기사 스니펫을 제공합니다.
  • KOSIS는 거시 승인실적 시계열을 제공해 개별 이벤트와 시장 전체 흐름을 같이 읽게 합니다.

운영자의 제어 명령이 백엔드를 거쳐 상태를 갱신하는 과정

운영 구조의 핵심

내부 사용자는 읽기 중심 경험을 기대하고, 운영자는 제어 중심 경험을 기대합니다. 현재는 둘 다 같은 백엔드 응답 계층과 일부 같은 API 도메인을 공유하고 있어서, 향후 카드사 확장 단계에서 사용자 경험과 운영 경험의 경계를 더 선명하게 다듬을 여지가 보입니다.

ingest와 extract 자동화 상세

start_ingest_run()진행 중 작업 여부를 확인하고 run_id를 발급한 뒤 백그라운드 스레드에서 회사별 ingest를 시작합니다.
run_ingest()registry 순회, company별 job row 생성, timeout 적용, 성공/실패/skip 집계, progress 상태 갱신까지 담당합니다.
run_extract_and_enrich()미추출 이벤트를 읽어 Playwright 상세 추출, 정규화, hybrid insight 생성, insight 저장, event update를 한 흐름으로 수행합니다.
run_full_pipeline()현재 구현상 ingest까지 포함하지 않고 이미 수집된 이벤트에 대한 extract/enrich 배치를 수행하는 경로로 사용됩니다.

브리핑 · 리포트 · snapshot 실행 상세

브리핑 데이터modules.briefing 가 expected companies, notable events, ending soon, company stats, category distribution을 계산해 일간/주간 payload를 만듭니다.
브리핑 발송/api/briefing/send-now 는 readiness 확인, HTML 렌더링, 수신자 결정, 이메일 발송, briefing log 생성까지 이어집니다.
리포트 스튜디오modules.report_studio 는 report type, basis, period 범위를 정규화하고 preview route URL과 snapshot manifest를 생성합니다.
dashboard snapshotmodules.dashboard_snapshot 는 dashboard/events/products/insights 탭별 snapshot과 stats, product news groups, company overview를 메모리에 캐시합니다.

job tracking 해석

  • ingest와 extract는 각각 job row를 만들고 상태를 pending → running → success/failed 로 이동시킵니다.
  • curator lock 같은 skip도 운영 관점에서는 job 상태와 last_error에 명시적으로 기록됩니다.

progress 해석

  • 진행률은 DB 테이블이 아니라 프로세스 메모리 상태에서 관리되고, API는 그 snapshot을 읽어옵니다.
  • 즉 현재 구조는 "실시간 운영 상태는 메모리, 장기 감사/이력은 SQLite" 식으로 역할이 나뉩니다.

리포트 artifact 해석

  • report studio는 basis 정규화 → preview URL 생성 → snapshot manifest 구성 → HTML/PNG/PDF materialize → DB row 보강 순서로 움직입니다.
  • 이 흐름 덕분에 동일한 데이터 기준으로 preview, file download, email send를 모두 연결할 수 있습니다.

briefing send-now 해석

  • payload 계산, readiness 판단, HTML 렌더링, SMTP 전송, DB 로그 기록이 하나의 호출에서 이어집니다.
  • 즉 브리핑은 단순 메일 유틸이 아니라 데이터 품질 점검과 발송 운영을 묶은 API입니다.
07

데이터 저장 구조

저장층은 단일 DB 하나가 아니라, 관계형 상태는 SQLite, 문서와 매니페스트는 data/, 벡터 검색은 Chroma, 산출물과 로그는 output/ 와 logs/ 로 나뉘어 있습니다.

database.py modules/product_links.py modules/rag/embedder.py modules/rag/collector.py

저장소 지도

이 프로젝트는 이벤트 모니터링 앱을 넘어 문서 저장소와 리포트 공장 성격도 같이 갖고 있습니다.

데이터 저장소 토폴로지
flowchart TB A["events.db"] --> A1["events"] A --> A2["event_snapshots"] A --> A3["event_sections"] A --> A4["event_insights"] A --> A5["manual edits and curation state"] A --> A6["jobs, briefing logs, reports"] A --> A7["products, launch facts, sync cursors, external signals"] B["data/card_terms"] --> B1["PDF originals"] B --> B2["manifest.json"] B --> B3["product_disclosures.json"] C["data/chroma_db*"] --> C1["active store"] C --> C2["legacy and recovered stores"] D["output/"] --> D1["briefings"] D --> D2["playwright captures"] D --> D3["server logs"] D --> D4["report artifacts"]

정형 데이터, 문서 원본, 벡터 인덱스, 산출물이 각각의 저장소로 분리된 구조

관계형 상태

이벤트 계열이벤트 본체, 스냅샷, 섹션, 인사이트, 조건 fact, 상품 링크
운영 계열jobs, sync cursors, external signals
사람 개입 계열manual edits, curation state, briefing logs, reports

문서 및 벡터 상태

약관/공시 원본data/card_terms 와 매니페스트 파일
벡터 저장소data/chroma_db 와 recovered/legacy 파생 디렉터리
산출물브리핑, 리포트, 캡처, 디버그 로그가 output/ 아래에 축적

주요 SQLite 모델군

  • CardEvent, EventSnapshot, EventSection, EventInsight 가 이벤트 수집 이후의 정형화 상태를 담당합니다.
  • EventProductLink, EventConditionFact 는 상품 및 조건 분석 결과를 붙입니다.
  • EventManualEdit, EventCurationState 는 사람 개입 이력을 남깁니다.
  • Job, BriefingLog, BriefingReport, Product, ProductLaunchDateFact, SyncCursor, ExternalSignalSnapshot 로 운영 상태를 확장합니다.

파일 기반 저장소 상세

  • data/card_terms/manifest.json 과 product_disclosures.json 은 문서 수집과 상품 공시 payload의 기준 파일 역할을 합니다.
  • modules/rag/embedder.py 는 data/chroma_db 를 기본 persist dir로 쓰고, chroma_db.active 마커로 활성 경로를 전환할 수 있습니다.
  • recovered/legacy/backup 디렉터리는 이관 · 복구 이력과 운영 히스토리를 파일 시스템에 남깁니다.

output 산출물 상세

  • output/briefings 는 브리핑 관련 산출물을 보관합니다.
  • output/playwright 는 캡처 및 렌더링 확인 결과를 남깁니다.
  • 루트 output에는 uvicorn 로그, report studio 로그, sync 결과 JSON 등 운영 디버그 자료가 함께 쌓입니다.

메모리 캐시와 snapshot 상태

  • dashboard snapshot은 DB에만 의존하지 않고 메모리 cache와 background refresh를 통해 탭별 응답 속도를 높입니다.
  • company brief, qualitative comparison, weekly AI insight 같은 응답은 별도 TTL 캐시를 사용해 반복 계산 비용을 줄입니다.
저장 구조의 설계 원칙

현재 저장 구조는 "모든 것을 DB 하나에 넣는 형태"가 아니라, 정형 상태는 SQLite, 문서 원본은 data 폴더, 검색 인덱스는 Chroma, 산출물과 운영 흔적은 output에 나누어 두는 운영형 배치 구조입니다. 이 분리가 있기 때문에 브리핑, 상품/RAG, 리포트, 공시 sync가 서로 다른 저장 성격을 유지한 채 함께 동작할 수 있습니다.

상품공시 수집과 출시일 authority

신한 상품공시AJAX 목록 API와 개정내용 상세 API를 순차 호출해 출시일, 시행일, 신규출시/개정 여부를 판정합니다.
삼성/현대/KB 공시삼성은 Playwright + 목록/상세 호출, 현대는 SSR HTML + PDF 조회 API, KB는 HTML 테이블 파싱으로 출시일과 발급중단일을 읽습니다.
product_disclosures.json카드사별 공시 결과는 먼저 파일 기반 disclosure projection으로 저장됩니다.
authority DBProduct 가 canonical product master, ProductLaunchDateFact 가 source별 launch-date evidence를 저장하고, 선택된 authority는 launch_date_source, launch_date_confidence, launch_date_source_ref 로 남습니다.

상품 카탈로그와 공시 저장 방식

hybrid mergemanifest.json, product_disclosures.json, Chroma 내부 catalog, SQLite products 테이블을 순차 합성해 최종 카탈로그를 만듭니다.
canonical overlayDB의 launch authority가 파일 · 문서 기반 정보 위에 마지막 overlay 역할을 해, 실무 화면에는 항상 정제된 canonical catalog가 보이게 합니다.
event linkageevent 텍스트에서 추출된 linked card는 이 canonical catalog와 매칭되어 EventProductLink row로 저장됩니다.

RAG chunking 기준

  • collector가 카드사별 약관 PDF를 모아 CardProduct 로 구성하고, summary/benefits_text/raw_text를 붙입니다.
  • streaming indexer는 chunk_card_product() 결과를 버퍼링한 뒤 100개 단위로 Chroma에 저장합니다.
  • chunk metadata에는 company, card_name, product_key, section, chunk_index 가 들어갑니다.

임베딩과 Chroma 구성

  • 임베딩 모델은 Gemini models/gemini-embedding-2-preview 를 사용합니다.
  • Chroma collection 이름은 card_products, distance 공간은 cosine 입니다.
  • PersistentClient 는 data/chroma_db 를 기본 persist dir로 사용하고, chroma_db.active 마커가 있으면 활성 경로를 오버라이드합니다.

RAG 입력 자산

  • 입력은 카드사별 상품공시/약관 PDF이며, data/card_terms/<issuer> 에 실제 파일이 저장됩니다.
  • manifest repair, local-only rebuild, new product detection 이 collector 레이어에 포함돼 있습니다.

RAG 검색 해석

  • semantic document search는 chunk 본문과 metadata를 함께 반환하고, lexical catalog search는 상품 메타와 요약 텍스트를 중심으로 작동합니다.
  • 즉 이 프로젝트의 검색은 "상품 메타 검색"과 "문서 청크 검색"이 분리돼 있습니다.
08

확장과 구조 효율화 포인트

현재 구조는 이미 많은 기능과 자동화 자산을 담고 있고, 그만큼 향후 확장을 위해 역할과 경계를 더 선명하게 다듬을 포인트도 잘 드러납니다. 앞으로는 카드사를 더 추가하고 기능을 보완해가면서 구조 효율화를 함께 진행하는 방향이 자연스럽습니다.

modules/connectors/* app.py modules/pipeline.py database.py

페이지 경계 포인트

공개 랜딩, 내부 실무, 운영 제어가 하나의 앱 설계 위에 올라가 있어 앞으로 사용자별 진입 경계를 더 선명하게 정리할 수 있습니다.

API 경계 포인트

조회 API와 운영 트리거 API와 동기화 시작 API가 같은 라우트 계층에서 함께 움직여, 도메인별 재배치 계획을 세우기 좋습니다.

프론트 경계 포인트

전역 스크립트가 여러 API 영역을 직접 알고 있어, 이후 화면 책임을 더 모듈화할 방향이 분명하게 보입니다.

데이터 plane 포인트

SQLite, 문서 폴더, Chroma, output 산출물이 각각 제 역할을 하고 있어, 향후 운영 기준에 맞춰 저장 책임을 정리하기 좋은 상태입니다.

확장 관점에서 보면

카드사를 더 붙일수록 커넥터와 정규화가 중심 seam이 되고, 그 결과는 대시보드 필터, sync 상태, 운영 버튼, 리포트 근거, 상품/RAG 검색까지 이어집니다. 그래서 As-Is를 꼼꼼히 보는 이유는 이미 만들어둔 자동화 자산을 잘 살리면서 향후 확장 순서와 개선 계획을 더 정확하게 잡기 위해서입니다.

카드사 확대와 함께 보완할 기술 축

connector 확장새 카드사를 추가할 때는 registry, 공통 RawEvent 계약, 기간/카테고리/위협도 정규화 규칙이 함께 확장됩니다.
운영 상태 표준화sync-status, jobs, progress API를 카드사/상품/공시/RAG 단위로 더 일관되게 확장할 수 있습니다.
브리핑 · 리포트 고도화자동화 자산이 늘어날수록 브리핑과 report studio의 근거 데이터도 더 풍부해질 수 있습니다.

구조 효율화가 자연스럽게 이어질 지점

pages 분리공개/내부/운영 페이지를 사용자 목적별로 더 선명하게 나눌 수 있습니다.
domain routers 분리현재 app.py 에 모여 있는 events, analytics, products, disclosures, rag, pipeline을 도메인별 라우터로 옮길 수 있습니다.
service/worker 분리자동화 흐름이 이미 뚜렷하기 때문에, 향후에는 service/worker 단위로 추출해도 의미가 잘 유지됩니다.
