# 브리핑 인텔리전스 개편 디자인 스펙

## 1. 배경

현재 운영 탭의 브리핑 기능은 운영자 관점의 발송 도구에 가깝다. 일간/주간 브리핑은 미리보기, 즉시 발송, 발송 로그 확인 정도만 제공하고 있으며, 본문도 신규 이벤트 수, 종료 임박 수, 발송 여부 같은 운영성 정보에 무게가 실려 있다.

하지만 실제 브리핑 독자는 운영 담당자가 아니라 마케팅 관련 의사결정권자다. 따라서 브리핑은 "운영 현황 보고"가 아니라 "경쟁 카드사 상품/이벤트 동향을 빠르게 읽어주는 인텔리전스 브리핑"으로 재정의되어야 한다.

## 2. 문제 정의

### 2.1 현재 브리핑의 한계

- 운영 탭 브리핑 UI가 발송 기능 위주라서 콘텐츠 품질 판단 근거가 부족하다.
- 일간/주간 브리핑 본문이 이벤트 개수, 종료 임박, 주목 이벤트 나열 중심이라 마케팅 의사결정에 바로 연결되기 어렵다.
- AI 요약이 있더라도 구조화된 근거와 함께 제시되지 않아 신뢰 가능한 브리핑으로 보이기 어렵다.
- 발송 로그가 단순 성공/실패 기록이라 "어떤 품질 상태의 브리핑이 나갔는지" 추적할 수 없다.
- 운영 탭 관련 JS가 템플릿 인라인 스크립트와 `static/js/dashboard.js`에 분산되어 있어 브리핑 UX 개편 시 변경 리스크가 크다.

### 2.2 현재 코드 구조

- 브리핑 생성/렌더링/발송/스케줄: `modules/briefing.py`
- 브리핑 API: `routers/briefing.py`
- 운영 탭 UI: `templates/simple_dashboard.html`
- 운영 탭 동작 JS: `static/js/dashboard.js`
- 발송 로그 저장: `database.py` 의 `BriefingLog`

## 3. 목표

### 3.1 제품 목표

- 운영 탭 안에서 브리핑을 관리하되, 브리핑 자체는 마케팅 의사결정자용 인텔리전스 산출물로 재구성한다.
- 브리핑을 읽는 사람이 3분 안에 "이번 경쟁사 동향의 결"을 파악할 수 있게 만든다.
- 운영자는 발송 여부를 시스템 상태가 아니라 콘텐츠 품질 상태를 보고 판단할 수 있어야 한다.
- 브리핑 로그는 단순 발송 이력이 아니라 품질 추적 이력으로 진화해야 한다.

### 3.2 비목표

- 기본 브리핑에 강한 처방형 "대응 시사점"을 필수 섹션으로 넣지 않는다.
- 운영 탭을 전체 파이프라인 관제 도구로 다시 설계하지 않는다.
- 브리핑 승인 워크플로우, 버전 diff UI, 협업 코멘트 같은 대형 기능은 이번 범위에 넣지 않는다.

## 4. 핵심 원칙

### 4.1 브리핑 관점

- 브리핑은 운영 정보가 아니라 경쟁 동향 요약이어야 한다.
- AI 서술은 제안형보다 관찰형 톤을 사용한다.
- 요약은 구조화된 데이터와 근거 이벤트에 기반해야 한다.
- 데이터가 부족하면 과감하게 "근거 부족" 상태를 보여주고 억지 요약을 만들지 않는다.

### 4.2 운영 탭 관점

- 운영 탭의 브리핑 영역은 "발송 버튼 모음"이 아니라 "브리핑 품질 관리 콘솔"이어야 한다.
- 운영 상태, 파이프라인 상태, 브리핑 품질 상태는 시각적으로 분리해야 한다.
- 발송 여부 판단에 필요한 정보는 상단에서 바로 보이게 한다.

## 5. 정보 구조

### 5.1 일간 브리핑

일간 브리핑은 "하루 동안 새롭게 포착된 경쟁 변화"를 빠르게 이해시키는 구조로 설계한다.

구성:

- 오늘의 한줄 동향
  - AI가 3~5문장으로 하루치 변화의 성격을 요약한다.
  - 예: 특정 카드사가 프리미엄/연회비 캐시백에 집중했는지, 생활밀착형 이벤트가 늘었는지 등.
- 카드사별 신규/강조 이벤트 요약
  - 신한, KB, 삼성, 현대 순 고정
  - 각 카드사별 신규 포착 건수와 대표 메시지, 대표 혜택 키워드 노출
- 오늘의 주목 패턴
  - 혜택 유형, 카테고리, 타깃, 메시지 키워드에서 반복되는 축을 AI가 묶어 설명
- 종료 임박/전환 포인트
  - 단순 종료 리스트가 아니라 어떤 테마의 이벤트가 빠지는지 보여줌
- 근거 이벤트
  - 위 요약을 설명하는 대표 이벤트 5~10건 카드 노출

### 5.2 주간 브리핑

주간 브리핑은 "일주일 동안 시장이 어떤 방향으로 움직였는지"를 읽게 하는 구조로 설계한다.

구성:

- 이번 주 시장 요약
  - AI가 주간 흐름을 하나의 짧은 내러티브로 설명
- 카드사별 동향 요약
  - 카드사별로 이번 주 상품/이벤트 톤을 2~4문장 요약
- 주간 테마 변화
  - 카테고리, 혜택 방식, 타깃 세그먼트, 메시지 키워드 변화
- 신규 상품/상품 공시 동향
  - 이벤트뿐 아니라 상품 공시와 신규 상품 흐름을 함께 요약
- 대표 사례
  - 이번 주를 설명하는 대표 이벤트/상품 카드

### 5.3 AI 생성 원칙

- AI는 전체 본문을 자유 생성하지 않는다.
- 서버가 먼저 회사별/테마별 구조화 payload 를 만들고, AI는 그 payload 를 요약하는 역할만 맡는다.
- AI 실패 시 rule-based fallback summary 를 사용한다.
- fallback 사용 여부는 운영 탭 품질 경고와 발송 로그에 남긴다.

## 6. 운영 탭 UX 설계

### 6.1 개편 방향

운영 탭의 브리핑 영역은 "운영 현황 표시"보다 "브리핑 품질 판단"에 집중한다.

권장 레이아웃:

- 상단: 일간 브리핑 카드, 주간 브리핑 카드
- 중단: 품질 경고 패널, 생성 결과 요약 패널
- 하단: 발송 액션, 발송 이력 로그
- 기존 파이프라인/수집/RAG 상태는 브리핑 관리 구역과 분리

### 6.2 핵심 컴포넌트

#### 브리핑 준비 상태 카드

일간/주간 각각에 대해 다음 정보를 노출한다.

- 생성 시각
- 대상 기간
- 근거 이벤트 수
- 상품 공시 반영 여부
- AI 요약 생성 상태
- 주요 섹션 생성 완료 여부

#### 품질 경고 패널

다음과 같은 경고를 노출한다.

- 신규 이벤트 0건
- 특정 카드사 데이터 부족
- 근거 이벤트 수 부족
- 상품 공시 데이터 미반영
- AI 요약 fallback 사용
- 대표 사례 부족
- 특정 섹션 비어 있음

#### 미리보기 및 발송 액션

- 일간 미리보기
- 주간 미리보기
- 일간 테스트 발송
- 주간 테스트 발송
- 일간 실제 발송
- 주간 실제 발송

초기 범위에서 실제 발송과 테스트 발송을 분리하기 어렵다면, 우선 `delivery_mode=test|production` 개념을 로그에 남길 수 있게 한다.

#### 발송 이력 로그

기존 성공/실패 로그 대신 아래 성격의 로그로 확장한다.

- 브리핑 유형
- 발송 시각
- 대상 기간
- 수신자 수
- 근거 이벤트 수
- 근거 상품 수
- 품질 경고 수
- AI 생성 상태
- delivery mode
- 실패 사유 또는 경고 요약

## 7. 백엔드 설계

### 7.1 계층 분리

현재 `modules/briefing.py` 는 다음 책임이 한 파일에 섞여 있다.

- 일간/주간 데이터 집계
- HTML 렌더링
- 이메일 발송
- 스케줄 잡
- 신규 상품 알림 렌더링

이번 개편에서는 파일 분리까지 반드시 하지 않더라도, 최소한 내부 함수 계층을 다음처럼 분리한다.

- raw collect layer
  - 이벤트/상품/로그 원천 데이터 조회
- briefing payload layer
  - 마케팅 인텔리전스용 구조화 데이터 생성
- summary generation layer
  - AI 또는 rule-based 요약 생성
- quality evaluation layer
  - 품질 경고 계산
- render layer
  - email/report HTML 렌더링
- delivery layer
  - 발송 및 로그 저장

### 7.2 신규 payload 구조

일간/주간 공통으로 아래 정보를 가지는 payload 를 설계한다.

- generated_at
- period_label
- report_type
- company_sections
- theme_summary
- product_summary
- evidence_events
- evidence_products
- quality_warnings
- ai_summary_status
- data_coverage

### 7.3 요약 데이터 생성

서버는 먼저 아래 구조를 계산한다.

- 회사별 신규 이벤트 수
- 회사별 대표 혜택/카테고리/메시지 키워드
- 주간 상위 카테고리/혜택 패턴
- 상품 공시 변화
- 종료 임박 이벤트 테마
- 대표 사례 후보

이 구조를 AI에 전달해 서술형 summary 를 생성한다.

## 8. 데이터 모델 변경

### 8.1 `briefing_logs` 확장

현재 `BriefingLog` 는 아래 필드만 가진다.

- briefing_type
- recipient_count
- new_events_count
- high_threat_count
- ending_soon_count
- status
- error_msg
- sent_at

마케팅 브리핑 품질 추적을 위해 아래 확장을 권장한다.

- period_label
- source_event_count
- source_product_count
- warning_count
- warning_json
- ai_summary_status
- delivery_mode
- template_version

초기 구현에서는 기존 집계 필드 일부를 유지하되, 의미가 모호한 `high_threat_count` 는 `notable_count` 또는 더 일반적인 의미의 요약 지표로 재정의하는 것이 좋다.

### 8.2 향후 확장 가능성

향후 브리핑 결과를 다시 재현할 수 있어야 한다면 별도 `briefing_snapshots` 테이블을 두고 payload JSON 을 저장하는 방향도 검토할 수 있다. 다만 이번 범위에서는 로그 확장만 우선한다.

## 9. API 설계 방향

### 9.1 기존 API 유지

- `GET /api/briefing/preview`
- `POST /api/briefing/send-now`
- `GET /api/briefing/logs`

### 9.2 신규 또는 확장 API

권장:

- `GET /api/briefing/status`
  - 일간/주간 브리핑 준비 상태와 품질 경고 반환
- `GET /api/briefing/preview?type=daily|weekly`
  - 기존 유지
- `POST /api/briefing/send-now?type=daily|weekly&mode=test|production`
  - 발송 모드 구분
- `GET /api/briefing/logs`
  - 확장된 로그 필드 반환

## 10. 프론트엔드 설계 방향

### 10.1 운영 탭 브리핑 UI

영향 파일:

- `templates/simple_dashboard.html`
- `static/js/dashboard.js`

개편 포인트:

- 브리핑 관련 인라인 스크립트와 외부 JS 중복 제거

### 10.2 템플릿 재구성

영향 파일:

- `templates/email_daily_briefing.html`

개편 포인트:

- 운영성 KPI 제거
- 동향 요약 섹션 강화

- 섹션이 비었을 때 graceful empty state 처리

## 11. 구현 단계

### Phase 1. 브리핑 콘텐츠 구조 개편

- 일간/주간 payload 재정의
- AI 요약 입력 구조 정리

- 이메일/주간 리포트 템플릿 재구성

- `briefing_logs` 스키마 확장

## 13. 리스크 및 대응

### 13.1 AI 요약 품질 불안정

- 구조화 payload 기반 요약으로 제한
- fallback summary 유지
- AI source/status 를 로그에 저장

### 13.2 데이터 편중

- 특정 카드사 이벤트가 과하게 많은 경우 요약이 왜곡될 수 있음
- 회사별 최소 보장 블록과 coverage warning 추가

### 13.3 프론트 코드 중복

- 운영 탭 관련 로직이 템플릿과 외부 JS에 동시에 존재
- 브리핑 UX 개편 시 관련 함수 정리 필요

## 14. 결론

이번 개편의 본질은 운영 탭에 있는 브리핑 기능을 없애는 것이 아니라, 운영 탭에서 관리하는 브리핑의 목적을 바꾸는 것이다. 즉 브리핑을 "발송 가능한 운영 결과물"이 아니라 "마케팅 의사결정자가 읽는 경쟁 동향 요약"으로 재정의하고, 운영 탭은 그 품질과 발송을 관리하는 콘솔로 바뀌어야 한다.
