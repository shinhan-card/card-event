# Card Event Intelligence Presentation Site UI/UX Upgrade Design

## 1. 배경

기존 `Card Event Intelligence` 프레젠테이션 사이트는 기본적인 정보구조와 이중 축 분리, 기술 배지 노출, 메인 `/`와 `/deep-dive`의 역할 분리를 이미 갖추고 있다.  
하지만 현재 상태는 다음 한계를 가진다.

- 첫인상이 충분히 프리미엄하지 않다.
- `/deep-dive`가 아직도 일부 구간에서 `텍스트 설명 + 카드 나열`에 가깝다.
- 비개발자에게는 설득력이 더 강해야 하고, 개발자에게는 구조 밀도가 더 높아야 한다.
- 이벤트 인텔리전스 축과 상품 / 공시 인텔리전스 축은 분리되어 있지만, 아직 “왜 다르게 설계되어야 하는가”가 장면 수준에서 충분히 강조되지 않는다.
- 상품 수집/적재/RAG 구성과 이벤트 해석 방식이 더 자세히 설명될 필요가 있다.
- 기술명, 파일명, 모듈명을 제외한 UI 문구는 전부 한국어로 정리되어야 한다.

이번 업그레이드는 단순 스타일 변경이 아니라, 기존 microsite를 `절제된 럭셔리 톤의 경영진용 시스템 쇼케이스 + 프리미엄 아키텍처 리뷰 문서`로 끌어올리는 전면 UI/UX 재설계다.

## 2. 목표

이번 UI/UX 업그레이드의 목표는 아래 세 가지를 동시에 달성하는 것이다.

- 압도적 첫인상
- 설득력 있는 정보 전달
- 전시형 인터랙션

단, 이 세 가지는 과잉 연출이 아니라 `절제된 럭셔리` 안에서 구현되어야 한다.

구체적 목표:

- 메인 `/`에서 10초 안에 “이 시스템은 단순 크롤러가 아니라 구조화된 인텔리전스 엔진이다”라는 인상을 준다.
- `/deep-dive`에서 텍스트 설명보다 구조도와 정보 위계가 먼저 읽히게 만든다.
- 이벤트 인텔리전스 축과 상품 / 공시 인텔리전스 축을 끝까지 분리해서 보여준다.
- 기술 스택이 추상 설명이 아니라 실제 처리 단계 위에 배치되어 읽히게 만든다.
- 기술명/파일명을 제외한 UI 레이어는 한국어 중심으로 정리한다.

## 3. 비목표

이번 업그레이드는 아래를 목표로 하지 않는다.

- 운영용 대시보드 추가 개발
- FastAPI 실서비스 UI 대체
- 실시간 데이터 연동 강화
- 모든 내부 로직을 코드 수준으로 완전 공개
- 디자인 시스템 패키지 분리

## 4. 핵심 하드 룰

이번 업그레이드에서 절대 깨지면 안 되는 규칙은 아래와 같다.

### 4.1 언어 정책

- 메뉴, 버튼, CTA, 네비게이션, 푸터, 캡션, 섹션 라벨, 보조 문구는 전부 한국어로 표기한다.
- 기술명은 실제 이름을 유지한다.
  - 예: `Playwright`, `Gemini`, `FastAPI`, `ChromaDB`, `RAG`
- 파일명/모듈명은 실제 이름을 유지한다.
  - 예: `modules/pipeline.py`, `routers/rag.py`
- `Overview`, `Primary`, `Shared Bridge`, `Control Plane` 같은 UI 문구는 허용하지 않는다.

### 4.2 구조 정책

- `/` 와 `/deep-dive`의 2단 구조는 유지한다.
- 메인은 가치 설득이 중심이다.
- 딥다이브는 구조 신뢰가 중심이다.
- 이벤트 축과 상품 / 공시 축은 시작부터 끝까지 시각적으로 분리한다.
- 두 축이 만나는 지점은 `공유 전달면`과 `운영 판단면`으로 제한한다.

### 4.3 표현 정책

- 텍스트는 구조도를 보조해야 한다.
- 구조도는 카드 묶음이 아니라 레이어, 레인, 연결선, 근거 레벨, 범례가 있는 도식으로 읽혀야 한다.
- 모션은 의미를 전달해야 하며 장식만을 위한 모션은 금지한다.

## 5. 대상 사용자

### 5.1 1차 사용자

비개발 이해관계자

- 경영진
- 투자/사업 검토자
- 제품 이해관계자

이들은 다음을 빠르게 이해해야 한다.

- 이 시스템이 왜 필요한가
- 왜 단순 수집기가 아닌가
- 어떤 구조적 강점이 있는가
- 왜 확장 가능한가

### 5.2 2차 사용자

개발자, 운영자, 기술 검토자

이들은 다음을 확인해야 한다.

- 두 축이 어떤 책임으로 분리되는가
- 각 단계에 어떤 기술이 놓이는가
- 실제 구현 근거가 어디에 있는가
- 어떤 부분이 현재 구현이고 어떤 부분이 승인된 설계인가

## 6. 디자인 방향

선택된 방향은 `Executive Atlas`다.

정의:

- 다크 네이비 기반
- 절제된 럭셔리
- 구조도 중심
- 보고서형 정보 위계
- 필요한 장면에만 강한 인터랙션

이 방향은 `브랜드 캠페인처럼 과한 전시형`이 아니라, `투자자/경영진 발표처럼 신뢰감 있고 고급스러운 시스템 프레젠테이션`을 목표로 한다.

## 7. 정보구조 재편

## 7.1 메인 `/`

메인의 핵심 질문:

`왜 이 시스템이 필요한가, 그리고 왜 이 구조가 경쟁우위가 되는가`

메인 장면은 아래 순서로 재편한다.

1. `시스템 선언면`
2. `두 축의 긴장`
3. `이중 엔진 보드`
4. `판단 전달면`
5. `시스템 가치`
6. `딥다이브 전환`

주의:

- 위 명칭은 설계 문서용 작업 라벨이다.
- 실제 UI 노출 라벨은 기술명/파일명/모듈명을 제외하고 전부 한국어만 사용한다.

### 7.1.1 시스템 선언면

목표:

- 한 문장으로 시스템을 정의
- 두 축 분리를 첫 화면부터 암시
- 프리미엄 톤 확립

필수 요소:

- 초대형 헤드라인
- 얇은 구조선 배경
- 좌우 분리된 축 프리뷰
- 1개의 강한 CTA + 1개의 보조 CTA

### 7.1.2 두 축의 긴장

목표:

- 이벤트 감시와 상품/공시 지식화가 서로 다른 질문이라는 점을 설명

표현:

- 텍스트보다는 `dual-plane diagram`
- 좌측은 시장 변화/이벤트 신호
- 우측은 상품 구조/공시 근거

### 7.1.3 이중 엔진 보드

핵심 구조:

- 메인 엔진 장면은 `하나의 단일 파이프라인`이 아니라, `두 개의 병렬 미니 레인 + 하나의 공유 전달면`으로 구성한다.
- 즉 이벤트 인텔리전스 축과 상품 / 공시 인텔리전스 축은 하나의 보드 안에서 보이더라도 서로 다른 레인으로 읽혀야 한다.

이벤트 레인:

- 수집
- 추출
- 정규화
- 규칙 기반 해석
- Gemini 보강
- 전달

상품 / 공시 레인:

- 소스 수집
- 적재
- 정제
- 청킹
- 임베딩
- 리트리벌 / RAG
- 전달

조건:

- `executive process board`처럼 보여야 한다.
- 각 단계에 기술 배지가 붙어야 한다.
- 두 레인은 색과 선 구조로 분리되어야 한다.
- 두 레인이 만나는 유일한 지점은 브리핑, 애널리틱스, 운영 판단 같은 공유 전달면이어야 한다.
- 최소 포함 기술:
  - `Playwright`
  - `BeautifulSoup`
  - `SQLAlchemy`
  - `Gemini`
  - `FastAPI`

### 7.1.4 판단 전달면

보여줘야 하는 것:

- 브리핑
- 애널리틱스
- 운영 판단
- 비교 검토

메시지:

- “이 시스템이 어떤 판단면을 만들어내는가”

### 7.1.5 시스템 가치

보여줘야 하는 가치:

- 더 빠른 경쟁 이벤트 파악
- 더 깊은 상품 근거 연결
- 더 신뢰도 높은 브리핑
- RAG 기반 지식축 확장성

### 7.1.6 딥다이브 전환

메시지:

- 메인에서 가치 설득이 끝났다면,
- 딥다이브에서 구조와 기술 신뢰를 확인하게 한다.

## 7.2 딥다이브 `/deep-dive`

딥다이브의 핵심 질문:

`이 시스템은 어떤 원리로 나뉘고, 어떤 기술과 모듈이 어떤 책임을 지는가`

딥다이브는 아래 순서로 재편한다.

1. `총괄 청사진`
2. `이중 축 거시 구조도`
3. `이벤트 해석 구조도`
4. `상품 / 공시 지식화 구조도`
5. `오케스트레이션 제어 보드`
6. `근거 기반 모듈 지도`
7. `원칙과 진화 보드`

주의:

- 위 명칭 역시 설계 문서용 작업 라벨이다.
- 실제 UI에 영어 섹션명이 직접 노출되어서는 안 된다.

## 8. 시각 시스템

### 8.1 컬러

기본 방향:

- 거의 검정에 가까운 다크 네이비
- 기본 포인트: `ice blue`
- 보조 포인트: `brass / warm amber`

원칙:

- 강한 대비
- 광택이 아니라 얇은 구조선과 패널 톤 차이로 고급감 형성
- 상태색은 운영 의미가 있을 때만 제한적으로 사용

### 8.2 타이포그래피

원칙:

- 헤드라인은 더 조형적인 display 계열
- 본문은 가독성 중심 sans
- 기술명/파일명/단계 번호는 tabular 또는 mono 성향이 느껴지게 처리

헤드라인 역할:

- 가치 선언
- 구조 전환
- 레이어 식별

본문 역할:

- 설명이 아니라 해설 캡션

### 8.3 그리드

메인:

- `12-column executive grid`
- 좌우 비대칭 분할 적극 활용

딥다이브:

- `report-like modular grid`
- 카드가 아닌 패널, 레인, 보드, 레이어 중심

### 8.4 패널 언어

패널은 아래 속성을 가져야 한다.

- 얇은 외곽선
- 내부 분할선
- 단계 번호 또는 레이어 키
- 기술 배지
- 짧은 해설

즉 단순 rounded card가 아니라 `structured panel`처럼 보여야 한다.

### 8.5 아이콘/그래픽

- emoji 금지
- 일관된 선형 SVG 사용
- 구조선, 노드, 레인, 칩, 범례가 주인공

### 8.6 모션

허용:

- Hero 진입 모션
- 레이어 점등
- 구조선 활성화
- 스크롤 기반 패널 reveal

제한:

- 장식 목적의 과한 parallax
- 의미 없는 floating animation
- 과도한 3D 연출

접근성:

- `prefers-reduced-motion` 엄격 대응

## 9. 딥다이브 구조도 설계

이번 업그레이드의 핵심은 총 7장의 구조도다.

## 9.1 총괄 청사진

구성:

- 좌측 상단: 이벤트 인텔리전스 입력면
- 좌측 하단: 상품 / 공시 인텔리전스 입력면
- 중앙 상단: 이벤트 처리 레일
- 중앙 하단: 상품 / 공시 지식화 레일
- 우측: 공유 전달면
- 상단: 핵심 기술 배지
- 하단: 근거 레벨

목적:

- 딥다이브 첫 화면에서 “두 개의 입력축이 각자 다른 처리 레일을 거쳐 하나의 전달면으로 연결된다”는 사실을 한 장으로 설명
- 이 장면은 단일 레일이 아니라 병렬 청사진이어야 한다.

## 9.2 이중 축 거시 구조도

구성:

- 좌측 대형 레인: 이벤트 인텔리전스
- 우측 대형 레인: 상품 / 공시 인텔리전스
- 하단/중앙 합류점: 브리핑, 애널리틱스, 운영자 검토

원칙:

- 두 축은 시각적으로 충분히 떨어져 있어야 한다.
- 연결선은 최소화한다.
- `같은 시스템 안의 별도 축`이라는 점이 명확해야 한다.

## 9.3 이벤트 해석 구조도

이벤트 축은 아래 단계로 분해한다.

1. 이벤트 수집
2. 상세 본문 추출
3. 구조 필드 정리
4. 규칙 기반 해석
5. Gemini 보강
6. 브리핑용 요약 / 인사이트 생성
7. 전달면 연결

설명 원칙:

- `AI가 전부 처리한다`는 인상을 주면 안 된다.
- 순서는 `구조화 -> 규칙 기반 해석 -> Gemini 보강`이어야 한다.
- 규칙 기반 해석은 안전망, 분류, 우선순위화 역할로 설명한다.
- Gemini는 요약, 해석 밀도 향상, 보강 계층으로 설명한다.

필수 노출 기술:

- `Playwright`
- `BeautifulSoup`
- `SQLite`
- `SQLAlchemy`
- `Gemini`

## 9.4 상품 / 공시 지식화 구조도

상품 / 공시 축은 아래 단계로 세분화한다.

1. 상품 / 공시 소스 수집
2. 원문 적재
3. 문서 정제
4. 청킹
5. 임베딩
6. 벡터 저장
7. 검색 / 리트리벌
8. RAG 응답 구성
9. 운영 / 브리핑 컨텍스트 연결

핵심 메시지:

- 이 축은 단순 수집이 아니라 `지식 기반을 구축하는 과정`이다.

필수 노출 기술:

- `PDF/HTML extraction`
- `Gemini embeddings`
- `ChromaDB`
- `RAG`

## 9.5 오케스트레이션 제어 보드

구성 컬럼:

- 스케줄
- 라우팅
- 축별 처리
- 저장
- 전달
- 운영 확인

표현 규칙:

- 각 칼럼은 2~3개의 작은 노드로 제한
- 노드 간 연결선은 명확
- 설명은 캡션 수준

## 9.6 근거 기반 모듈 지도

구성:

- 공유 코어
- 이벤트 축
- 상품 / 공시 축

각 모듈 클러스터는 반드시 아래 정보를 가진다.

- 대표 책임
- 실제 파일
- 사용 기술
- 근거 레벨

근거 레벨 표현:

- 실선 = 현재 구현 근거
- 점선 = 승인된 설계

## 9.7 범례

반드시 들어가야 하는 범례:

- 선 종류 의미
- 패널 톤 의미
- 칩 색 의미
- 근거 레벨 의미

## 9.8 원칙과 진화 보드

`설계 원칙 / 진화`는 텍스트 카드 부록이 아니라, 페이지를 닫는 마지막 구조 보드로 정의한다.

구성:

- 좌측: 설계 원칙 보드
- 우측: 진화 로드맵 보드

설계 원칙 보드에서 보여줘야 하는 것:

- 두 축 분리
- 규칙 기반 안전망
- 공유 전달면
- 실제 코드와 승인된 설계의 구분

진화 로드맵 보드에서 보여줘야 하는 것:

- 브리핑 인텔리전스 고도화
- 상품 / 공시 지식축 확장
- 운영자 판단면 강화

형식:

- 카드 나열이 아니라, 얇은 연결선과 단계 표식이 있는 보드
- 각 원칙과 로드맵은 짧은 캡션 + 상태/단계 표식으로 설명
- 이 장면 역시 `diagram-first`여야 한다.
